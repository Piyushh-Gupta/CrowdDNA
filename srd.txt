1. Introduction
1.1 Purpose
This Software Requirements Document (SRD) defines the functional and non-functional requirements, system architecture, technology stack, and delivery workflow for 
CrowdFlow
 DNA, a graph-based crowd interaction 
modeling
 system. It serves as the reference blueprint for development, evaluation, and demonstration of the project, and establishes a shared understanding of scope between the developer and any reviewing party.
1.2 Scope
CrowdFlow DNA analyzes an uploaded crowd video to produce risk-classified output, moving beyond simple occupancy counting. The system detects and tracks individuals, constructs a dynamic interaction graph representing spatial and kinematic relationships between people, and applies a Graph Neural Network (GNN) combined with a temporal model to classify localized crowd risk into discrete categories (Safe, Congesting, Critical) over time.
The system is scoped as a portfolio-grade demonstration project. It is explicitly NOT scoped to:
Provide real-time (live webcam, sub-second-latency) crowd monitoring in its initial release.
Provide certified, liability-bearing safety guarantees for deployment at real public events.
Generalize across all venue types without additional domain-specific tuning.
In-scope deliverables include: a trained detection/tracking/graph/GNN pipeline, a deployed inference demo accepting uploaded video, and an annotated output (bounding boxes, interaction graph overlay, risk heatmap, risk timeline).

2.6 Success Criteria
The project is considered successful as a portfolio-grade deliverable when the following criteria are met:
A working end-to-end demo is publicly deployed on Hugging Face Spaces (free CPU tier) and accepts an uploaded video clip without manual intervention.
All High-priority functional requirements (FR-001–FR-007) are planned to be implemented and demonstrable on representative test clips.
Risk classification achieves a minimum weighted F1 score of ≥ 0.75 across Safe / Congesting / Critical classes on held-out simulated and public benchmark clips (see Section 6.6).
End-to-end processing of a 30-second, 480p clip completes within the target processing time defined in Section 3.2.1 on the deployment CPU tier.
The detection/tracking stage achieves an acceptable ID-switch rate and MOTA score on the PETS2009/UMN benchmark subset (thresholds defined in Section 6.6).
The codebase passes CI linting and the automated smoke test (Section 6.2) on every push to main.
A reviewer or interviewer can understand the system design, methodology, and results from the README and live demo without requiring additional verbal explanation.
2.7 Known Limitations
The following limitations are inherent to the project's zero-cost, portfolio-grade scope and are disclosed rather than concealed:
Simulated training data (
PySocialForce
) approximates but does not fully replicate real panic/stampede dynamics; a 
sim
-to-real gap remains, as noted in Section 2.5 and addressed only as future work under Crowd Simulation Learner (Section 7.3).
The system does not support true real-time or live-camera monitoring in this release; free-tier CPU inference bounds throughput below live frame rates.
The model has not been validated across all venue types, camera angles, or crowd densities outside the training distribution.
Risk-class thresholds (Safe / Congesting / Critical) are calibrated on a limited data volume due to free-tier compute and session-time constraints.
Tracking accuracy degrades under heavy occlusion or extremely dense crowds — an inherent limitation of single-camera, 2D multi-object tracking.
The system is not certified and must not be relied upon for safety-critical or liability-bearing deployment at real public events (see Section 1.2).
No multi-camera or cross-camera re-identification support exists in this release (see Multi-Camera Memory, Section 7.2, for the roadmap item).

4.4 Architectural Style/Pattern
The system follows a modular pipeline (pipe-and-filter) architecture for its current MVP, rather than a microservices or monolithic web-application pattern. Each stage (detection, tracking, graph construction, GNN inference, rendering) is planned to be implemented as an independently callable module, composed sequentially by an orchestration layer within the demo application. This style was chosen for its simplicity, ease of local testing per stage, and suitability for a single free-tier deployment target.
Beyond the MVP, the project is architected to evolve from a single application into a modular, three-layer platform. This layering is a design and roadmap construct, not a change to the current deployment target: only the Core Engine layer is planned for the present release. The three layers are:
Core Engine — the planned MVP detection, tracking, interaction-graph, and GNN risk-prediction pipeline described in Sections 3 and 4.5. This is the only layer in scope for the current MVP.
Intelligence Modules — named, pluggable capabilities built on top of the Core Engine's outputs (tracks, interaction graphs, embeddings). Each module consumes Core Engine output and adds a specific predictive or analytical capability. Detailed in Section 7.2.
Research Modules — exploratory, long-term capabilities that extend beyond the current data, compute, and scope constraints. Detailed in Section 7.3.
This layered separation allows the Core Engine to remain a small, well-tested, independently demonstrable system, while Intelligence and Research Modules are documented as optional extensions rather than dependencies of the base system.

4.6 AI Model Design
This section details the model architecture choices underlying each stage of the Core Engine, expanding on the components introduced in Section 4.5.
4.6.1 Detection
YOLOv8n (nano variant), pretrained on COCO, used out-of-the-box or lightly fine-tuned on crowd-scene imagery; inference restricted to the 'person' class.
Confidence threshold is externalized to configuration (Section 3.2.5) to allow tuning precision/recall trade-offs per deployment scenario.
Architectural choice rationale: YOLOv8n is selected for its balance of detection accuracy and inference speed on CPU-constrained hardware. The nano variant minimises memory footprint while achieving competitive precision on pedestrian detection tasks, making it well-suited to the free-tier deployment environment. Restricting inference to the 'person' class further reduces per-frame latency.
4.6.2 Tracking
ByteTrack
 associates detections across frames using a two-stage matching strategy (high-confidence then low-confidence boxes) combined with a Kalman-filter motion model, preserving identity through brief occlusions.
Architectural choice rationale: 
ByteTrack
 is chosen because it achieves strong multi-object tracking accuracy without requiring appearance features (re-ID embeddings), keeping the implementation lightweight and dependency-free. Its two-stage matching strategy — associating high-confidence detections first, then recovering low-confidence boxes — improves track continuity under partial occlusion, which is common in dense crowd scenes.
4.6.3 Interaction Graph Construction
Nodes represent tracked individuals present in a given frame; edges connect pairs within a configurable proximity radius.
Edge features: inter-person distance, relative velocity divergence, and local density gradient (Section 3.1, FR-005).
Graph Construction Method: Edges are created between any two tracked individuals whose centroids fall within a configurable proximity radius (distance threshold). This radius-based approach is chosen for its simplicity and direct correspondence to physical crowd proximity, which is a primary indicator of congestion risk. The radius value will be treated as an externalized configuration parameter (Section 3.2.5) to allow tuning per venue type and camera resolution.
Planned Node Features: Each node in the interaction graph represents one tracked individual and is planned to carry the following per-frame features:
(a) 2D centroid position (x, y) in image coordinates, normalised to frame dimensions.
(b) Instantaneous velocity vector (
vx
, 
vy
), estimated from centroid displacement between consecutive sampled frames.
(c) Bounding box dimensions (width, height), as a proxy for the individual's apparent size and distance from camera.
(d) Local crowd density estimate: the count of neighbouring nodes within the proximity radius, normalised by area.
Planned Edge Features: Each edge between two nodes (individuals within the proximity radius) is planned to carry the following relational features:
(a) Inter-person distance: Euclidean distance between the two centroids.
(b) Relative velocity divergence: magnitude of the difference between the two velocity vectors, indicating whether the pair is moving toward or away from each other.
(c) Local density gradient: change in local density between the two nodes' neighbourhoods, indicating whether the area between them is becoming more or less crowded over time.
Architectural choice rationale: Graph Attention Network (GAT) is selected as the GNN encoder because its attention mechanism allows the model to learn which neighbouring individuals are most relevant to the risk state of a given node, rather than treating all neighbours equally. During training, GAT learns attention coefficients to dynamically determine the importance of neighboring nodes. This is particularly important in crowd analysis, where a single high-velocity or rapidly-converging pair may dominate the risk signal in an otherwise calm region. GAT's interpretable attention weights also support the planned explainability enhancements noted in Section 7.1.
4.6.4 GNN and Temporal Model
A Graph Attention Network (GAT) encoder performs message passing (number of rounds to be finalized) over each per-frame interaction graph to produce node/region embeddings.
A GRU-based temporal layer consumes the sequence of per-window graph embeddings to model how risk evolves over time, rather than classifying each frame in isolation.
A softmax classification head outputs one of three risk classes (Safe / Congesting / Critical) per spatial region per time window, together with a confidence score derived from the Softmax output probabilities.
Definition of 'Region': Throughout this document, a region refers to a spatial cell within a uniform grid overlaid on the video frame. For planning purposes, the frame is intended to be divided into a grid of equal-sized cells (e.g., a configurable N×M grid). Each cell constitutes one region. The GNN aggregates embeddings from all tracked individuals whose centroids fall within a given cell to produce a single per-region embedding, which the classification head then maps to a risk label. The specific grid resolution will be determined during implementation based on typical crowd density and frame resolution; it is treated as an externalized configuration parameter. This grid-based definition applies wherever 'per-region risk classification' is referenced in Sections 3, 4, and 6.
Architectural choice rationale (GRU): A Gated Recurrent Unit (GRU) models temporal risk evolution, capturing sequential state dependencies. GRU is preferred over LSTM for its simpler gating structure, which reduces parameter count and training cost under free-tier constraints (Section 2.4).
4.6.5 Training and Export
Training uses supervised learning on simulated (PySocialForce-labeled) sequences supplemented with public abnormal-crowd-behavior datasets, using a suitable loss function (e.g., class-weighted cross-entropy or focal loss), to be finalized during experimentation to address class imbalance toward the Critical class.
The trained PyTorch model is scripted/traced and exported to ONNX for portable, dependency-light CPU inference at serve time (Section 3.2.6).
4.6.6 Training Pipeline
The planned end-to-end training workflow proceeds through the following ordered stages. This is a design-level description; specific tools, hyperparameters, and dataset statistics will be documented during implementation.
Stage 1 — Dataset Preparation: Simulated pedestrian trajectories are generated using 
PySocialForce
 and risk labels are assigned using simulation-internal state (Section 4.7.2). Public benchmark clips (UMN, PETS2009) are processed and mapped to the three-class schema. The combined dataset is split into stratified train / validation / test sets (Section 4.7.3).
Stage 2 — Detection and Tracking: YOLOv8n is run on each video clip to produce per-frame person bounding boxes. 
ByteTrack
 is applied to assign persistent track IDs and compute per-track velocity vectors.
Stage 3 — Interaction Graph Construction: For each sampled frame, a per-frame interaction graph is built from the tracked individuals using the proximity-based method described in Section 4.6.3, producing PyTorch Geometric Data objects carrying planned node and edge features.
Stage 4 — GAT Training: The GAT encoder (Section 4.6.4) is trained on sequences of per-frame interaction graphs using a suitable supervised loss function (e.g., class-weighted cross-entropy or focal loss), to be finalized during experimentation based on class imbalance and validation performance. Interaction graphs are batched using PyTorch Geometric's batching mechanism during training. Training is performed on Google Colab (free GPU tier), where free-tier runtime limits may require multiple training sessions, with checkpointing used to resume training (Section 6.7, R-02).
Stage 5 — GRU Temporal 
Modeling
: The GRU temporal layer (Section 4.6.4) is trained jointly with the GAT encoder, consuming sequences of per-window graph embeddings to learn risk evolution over time. The combined GAT + GRU + classification head is trained end-to-end.
Stage 6 — Evaluation: The trained model is evaluated on the held-out test set using the metrics defined in Section 6.6 (Weighted F1, Accuracy, ROC-AUC, MCC, ECE). If time permits after completion of the MVP, an optional graph-feature ablation study may be conducted to evaluate the contribution of individual edge features.
Stage 7 — Model Export (ONNX): The trained PyTorch model is scripted or traced and exported to ONNX format (Section 4.6.5). The ONNX artifact is validated against the PyTorch model outputs on test samples to confirm numerical equivalence.
Stage 8 — Deployment: The ONNX model is committed to the project repository. The 
Gradio
 web application loads the ONNX artifact via ONNX Runtime at startup and exposes it through the demo interface on Hugging Face Spaces (free CPU tier), as described in Section 6.4.

4.7.3 Splitting, Balancing, and Augmentation
Train / validation / test splits are stratified both by risk-class distribution and by data source (simulated vs. public real footage), so validation performance separately reflects in-distribution and sim-to-real generalization (Section 2.5, 2.7).
The Critical class, naturally rare, is addressed via oversampling and/or class-weighted loss during training (Section 4.6.5).
Augmentation includes temporal jitter, spatial flips, and simulation-side variation of camera perspective and crowd density to increase scenario diversity within the zero-cost constraint.

7. Future Considerations / Roadmap
This section documents the project's evolution from a single application into a modular, three-layer platform: the Core Engine (planned MVP), Intelligence Modules (near-to-medium-term, pluggable), and Research Modules (long-term, exploratory). Only the Core Engine is a committed deliverable of the current MVP defined in Section 3. Intelligence and Research Modules are documented to establish architectural direction and research awareness; they should be presented to reviewers as roadmap and vision, not as work completed or in progress.
7.1 Layer 1 — Core Engine (Planned MVP Scope)
The Core Engine is the foundation all other layers build on. It corresponds directly to the functional requirements in Section 3.1, the components in Section 4.5, and the model design in Section 4.6:
Detection — YOLOv8n person detection per frame.
Tracking — 
ByteTrack
 persistent identity assignment across frames.
Interaction Graph — per-frame graph construction with proximity, relative-velocity, and density-gradient edge features.
GNN Risk Prediction — GAT + temporal (GRU) model producing the Safe / Congesting / Critical classification.
Recommended near-term hardening of the Core Engine, feasible within the zero-cost constraint, before building Intelligence Modules on top of it:
Richer graph edge features — heading similarity, acceleration, trajectory curvature, interaction duration, local clustering coefficient.
Multi-class risk severity (Very Low / Low / Moderate / High / Critical), extending the existing 3-class output head.
Basic uncertainty estimation (e.g., MC-dropout or a small ensemble) attached to each risk prediction.
Explainable AI (feature importance) via 
torch_
geometric.explain
 or attention-weight visualization on the GAT layer.
7.2 Layer 2 — Intelligence Modules (Near-to-Medium-Term, Pluggable)
Intelligence Modules are independent capabilities that consume Core Engine output (tracks, interaction graphs, risk embeddings) without modifying the Core Engine itself. Each is designed to be addable/removable without breaking the base pipeline.
PanicWave
 Predictor
Spatio
-temporal risk prediction — forecasting crowd risk state 3–10 seconds ahead of the current frame.
Early panic prediction and stampede probability estimation, built on the forecasted risk state.
Risk evolution timeline prediction, extending the existing risk timeline (Section 3.4.1) with a forecast horizon.
Crowd Energy Map
Perspective-aware density estimation and a continuous crowd 'energy' surface derived from local velocity/acceleration magnitude, as a complement to the discrete risk heatmap.
Real-time crowd heatmap and region-based risk statistics for the dashboard (Section 3.3.1).
Queue Intelligence
Bottleneck forecasting and exit-congestion prediction based on flow-rate analysis at defined ROIs.
Automatic Region of Interest (ROI) detection, to identify queue/choke points without manual configuration.
Conflict Predictor
Edge risk prediction — anticipating dangerous pairwise interactions before they occur, using the existing interaction-graph edge features.
Crowd 
behavior

EscapeRoute

Crowd flow simulation and dynamic evacuation route recommendation, using Core Engine risk output as a cost input to a routing algorithm.
Multi-Camera Memory
Multi-camera crowd tracking and cross-camera person re-identification, extending single-camera tracking to a multi-view setting.
Occlusion handling and recovery, improving track continuity within and across camera views.
Supporting analytics and deployment items relevant across Intelligence Modules:
Explainable risk reports and feature-contribution visualization per module.
Interaction graph visualization, event replay/playback, and AI decision logs.
Downloadable analytics report (PDF/CSV) and incident playback interface.
Cloud-based inference API with REST/WebSocket support, to serve modules independently of the demo UI.

7.4 Evaluation Metrics Roadmap
The current, formalized evaluation metrics used to assess the MVP are defined in Section 6.6. As Layer 1 hardening items (Section 7.1) are added — multi-class severity, uncertainty estimation, explainability — 
the metric set is expected to expand to include calibration error across additional classes and attention-weight-based explainability scores.
7.5 Scalability Plans
Migration from CPU-only inference to a paid or sponsored GPU tier if concurrent multi-user demo load, or any Layer 2/3 module, exceeds free-tier capacity.
Introduction of a lightweight persistent store (e.g., SQLite or another lightweight embedded database) if multi-session history or comparative analysis across uploads is required.
A plugin-style module interface (each Intelligence/Research module consuming a stable Core Engine output contract) to allow modules to be added without modifying the Core Engine.
